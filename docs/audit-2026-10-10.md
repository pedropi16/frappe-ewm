# Audit of frappe_wms (flow, design, usability, SAP EWM comparison) - 2026-10-10

## How it was done
| Check | What was run |
|---|---|
| Data integrity, production | the 13 ledger/stock/HU/delivery invariants (`tests/load/invariants.py`, read-only) on PLT1, DC1, DC2, DC3 |
| Multi-user load, dev site | `tests/load/seed_dc.py` (Madrid DC: ~340 bins, 200 products, 24 RF resources, ~26 users) then `simulate.py`, two runs of 6 and 5 minutes (about 5,900 and 5,000 HTTP calls) with receivers, pickers, loaders, packers, counters, order clerks and a "chaos" actor racing the same lines; invariants again after each run |
| Permissions | every whitelisted endpoint read for a role check (14 had none within two call levels), then probed over HTTP as a user with no WMS role |
| Database | row counts, indexes, `EXPLAIN` of the hot lookups |
| Usability | 17 desktop screens and the RF app captured in a browser and looked at |
| SAP | SAP help (S/4HANA 2025 FPS02) read by a research agent on 12 topics; each finding below says what is documented and what is inferred. Not verified against a live SAP system |

Limits: load ran on the dev server (one box, MariaDB shared with the browser tests), not the production gunicorn stack, so absolute timings are indicative and relative changes matter. The SAP help gave no screen layouts and no lock-concept page. Accessibility (screen reader, keyboard-only) was not tested.

## Results

### Data integrity - good
- Production, all four warehouses: 0 violations on all 13 checks.
- After both load runs (about 10,900 calls, with deliberate races on one receipt line, one task, one idempotency key): 0 violations. Ledger = balances = ERPNext stock, no negative stock, no double posting, no HU in two bins.

### Load and concurrency
| | Run 1 (before indexes) | Run 2 (after indexes) |
|---|---|---|
| calls / errors | 5,882 / 300 | 4,984 / 478 |
| goods receipt p50 / max | 0.81 s / 6.9 s | 0.30 s / 11.8 s |
| release wave p50 | 0.83 s | 0.34 s |
| confirm task p50 | 0.07 s | 0.06 s |
| pull next warehouse order p50 | 0.01 s | 0.01 s |
| HTTP 500 (deadlock/snapshot conflict) | 7 | 1 |

(Different seeds and traffic mix, so read the p50 drop and the fall in 500s as a direction, not a measurement.)

Errors by cause (run 1; run 2 is the same shape):
1. **Customer-return receipts fail again and again** (229 / 433 calls). The return Inbound Delivery is built from a Delivery Note but its lines do not carry the note row's batch (or serial numbers). The receiver then scans a batch that is not on that Delivery Note, and ERPNext refuses it only when the Goods Receipt is submitted. The delivery stays in every receiver's list and cannot be received. Same failure class the code comment mentions ("888 failed receipts"). **Defect.**
2. 54 "Scan the source Handling Unit before confirming" - the load script does not scan, the rule (HU source must be scanned over HTTP) is correct. Not a defect.
3. 7 HTTP 500 `QueryDeadlockError 1020` (6 on `frappe.client.submit` of a Sales Order against ERPNext's `tabBin`, 1 on `confirm_task` on a hot Handling Unit after the 4 retries). The WMS endpoints retry; ERPNext's own `submit` does not. **Minor, 1-2 % of those calls.**
4. Expected business refusals: over-receipt races ("only 83 left to receive, 233 scanned... may have been received on another scanner"), HU-count capacity, already-on-a-shipment. These show the race protection working.

### Security and permissions
- DocType permissions hold: a user with no WMS role gets 403 listing stock balances, tasks, deliveries, HUs, ledger.
- **Found and fixed: any logged-in user could take locks.** `locks.acquire_lock/renew_locks/...` had no role check, so a user with no WMS role could lock any task, delivery or HU against the operators, indefinitely (renewing). Now needs a WMS role. Same for `labor.stop_indirect_labor` and `posting_change.check_lines`.
- Mass-processing endpoints (`process_lines`, scrap, posting) only enforce roles line by line inside the loop; an unauthorised call returns per-line errors, not a 403. Acceptable, but a front check would be cleaner.
- `docs.webhook_events` is readable by any logged-in user (it only lists event names).

### Database and performance
At 600 tasks / 270 allocations the hot lookups were already full table scans (`EXPLAIN type=ALL`): tasks by Warehouse Order, by Stock Allocation, by source HU; Stock Allocation by delivery (every delivery screen); the open Warehouse Order lookup (every task creation); Warehouse Request by reference. Harmless now, quadratic with a real day's volume. **Fixed**: indexes added in `db_maintenance.INDEXES` (applied on every migrate); all six lookups now use an index. Ledger and balance tables were already indexed.

### Usability and design
Desktop (screenshots):
- The worklist screens (ad hoc HU/product, posting, scrapping, delivery list) are consistent and match the SAP worklist idea: find bar, marked-row grid, detail form, Mass Change, result column, status bar, popup on refusal.
- The left **Pages list is not organised**: 13+ pages in no process order, two different workspace sidebars ("WMS Core", "WMS"), and the delivery pages open with an empty sidebar and **no page title / breadcrumb**.
- Standalone pages (Alerts, Packing Center, Yard...) open as an empty screen asking "Select a warehouse", with a one-entry left column that wastes a third of the width.
- Monitor "Transactions" entries are plain unstyled links under the view list.
- The grid's "Group by (none) / then... / then..." takes three stacked controls on every list; collapse it under a button.
- Outbound Delivery shows status **"Draft" after it is submitted** (the field has Draft/Open/Allocated/...; "Open" is never set), which reads as "not released".
- Cells needing input are hard to tell from read-only ones (pale grey fields).
RF (phone): clear and fit for gloves: big targets, step bar, the expected scan shown above the field, Exception always at hand. Icons did not render in the headless browser (font), check on a real device.

### Flow and logic findings (code)
- Return deliveries drop batch/serial (above).
- A posting change that moves part of a quantity creates two stock lines in one bin but skips the bin's mixing rules (`validate_destination_bin` is deliberately not called). SAP requires mixed storage to be allowed for this, or a task with posting after the task. Result here: mixed stock types / products in a bin that forbids them.
- Partial moves now go to a pick HU, serial/batch are asked in the foreground (both added earlier today), but only the desk Confirm dialog, the RF task and RF Move ask: any other caller still gets the server refusal.
- `Warehouse Order` pull order is priority then age; SAP: latest start date, then priority, within the queue sequence.

## Re-run after the fixes (same dev site, seed 7, 6 minutes)

| | run 1 | run 2 (indexes) | run 3 (returns + submit retry) | final |
|---|---|---|---|---|
| HTTP calls | 5,882 | 4,984 | 6,054 | 6,063 |
| HTTP 500 | 7 | 1 | 33 | 2 |
| invariants | 0 | 0 | 0 | 0 |

- Customer returns: 712 refusals in one run were the simulator scanning an invented batch; returns now only take back the shipped batch/serial (shown on the RF Receive line, used by the simulator), so the receipt no longer sticks at the ERPNext mirror.
- ERPNext `submit` 500s: 6 -> 0 (submit/save wrapped in the deadlock retry).
- Run 3 exposed the real cause of most remaining 500s: MariaDB 11.8 `innodb_snapshot_isolation=ON` turns every contended locking read (naming series counter, a bin's Handling Units) into error 1020 once the other transaction commits. Switching it off globally was tried and REJECTED: ERPNext's non-locking Bin update then loses updates (Bin under-counted by 89-120 units, caught by the `erpnext_bin_cache` invariant). It is now relaxed only around WMS's own lock reads and document naming (`concurrency.latest_committed_locks`, `insert_hot`).
- A deadlock inside the auto goods issue was swallowed by its savepoint guard and then failed on "SAVEPOINT does not exist" (2 x 500); it now propagates to the endpoint retry.
- Goods receipt p50 is 1.25 s here against 0.30 s in run 2: the dev DB has grown through six runs and one server serves everything; not re-measured on a clean DB.
